# SN87 miner guide

Walkthrough, about 75 minutes in one sitting. You are a competent miner who has never seen SN87.
You install it, run the public demo, serve a method on your own machine, score it against
published truth, run the signed endpoint that validators call, sign an announcement for it, and
learn what is left to do on the public test network, number 582.

**This guide does not end at a score on 582, and it says so up front.** The last step of a miner's
route is "uid N received a non-zero score in window W on 582". You cannot complete that step
from this guide alone: it needs your uid to be on the shadow allowlist and a window to have
closed. A shadow cohort is described in [shadow-cohort.md](shadow-cohort.md): shadow results are
scored and published but not weighted. This guide does not claim that any uid is enrolled or that
a window has run, and no outside uid is known to be scored by this repository's tooling. Part F
states exactly what must exist before the step can be completed, and what you will check when it
does. Parts A and B are real. Parts C and D are rehearsals on your machine, with public fixtures
and a throwaway key. Part E is a list of operator actions. Nothing in this guide sends anything
to a chain.

The guide is written once, here. `scripts/run_guide.py` runs its commands and compares the output
with the blocks below. The offline parts run on every change, on Linux and macOS. The one command
marked `network` (Part E) runs in a separate job that does not block merges, and the commands
marked `requires-valkey` (Part D) run wherever a Valkey-compatible server is installed, which CI
guarantees. The format is described in [guide-format.md](../protocol/guide-format.md). Nothing in
the guide is copied by hand from a run: the registration cost in Part E is read from the chain
when you run the step.

**Why it is safe.** The commands write only inside the folder you clone, in uv's package cache
and in a throwaway replay store you start yourself. The key in Part D is generated by the guide
for this rehearsal only. You need no wallet and no account until Part E, and Part E is a list of
things you do with your own tools, which the guide does not do for you.

| Part | What | Time | Real or rehearsal |
| --- | --- | --- | --- |
| A | Requirements and platform policy | 5 min | real |
| B | Install and run the public demo | 10 min | real |
| C | Write a method, serve it locally, score it against published truth | 15 min | rehearsal on public fixtures |
| D | The signed endpoint, probe and announcement | 20 min | rehearsal with a throwaway key |
| E | Registration and test funds on 582 | 10 min | operator actions, not performed here |
| F | The first score on 582 | 5 min | depends on the shadow cohort allowlist; plus a rehearsal on a demo window |
| G | Troubleshooting by error code | as needed | reference |
| H | Report back | 5 min | real |

## Part A. Requirements and platform policy

**Platforms.** Linux and macOS are supported and tested in CI on Python 3.12 and 3.13. Windows is
supported through WSL2. Native Windows is not supported (the [README](../../README.md) says why).

**What you need, and when.**

| Need | For | Needed from |
| --- | --- | --- |
| `git`, `curl` and [uv](https://docs.astral.sh/uv/) | everything; uv fetches Python 3.12 or later; `curl` talks to the local servers | Part B |
| A Valkey-compatible server (Valkey or Redis) with `maxmemory-policy noeviction` | the replay store of the signed endpoint, so a replayed request is refused | Part D |
| A public HTTPS origin in front of your endpoint (a reverse proxy with TLS) | a real announcement; validators call HTTPS for any remote host | Part E |
| A wallet of your own with a registered hotkey on netuid 582 | being a miner on the network | Part E |
| Test funds for the registration cost | registering that hotkey | Part E |

No hardware or timing figure is published for a miner. The measurements in this repository are
local and deterministic and are not network, signing, TLS or model-inference capacity. Measure
your own engine.

What a miner does is in the demo output. A capsule is a bounded, canonical JSON object of
evidence. The miner returns one differential: `FINDINGS` (with an exact code, a confidence and
evidence references), `NO_MATERIAL_DEVIATION`, or `INSUFFICIENT_EVIDENCE_ABSTAIN`. Evidence credit
is binary, so cite every required reference. A missing or late response counts as a raw failure.
The scorer is public and the truth of these three fixtures is published, which is why you can
reproduce every number above. The truth of hidden instances is private.

## Part C. Write a method, serve it locally, score it

A method is one function: one capsule in, one differential out. You will write the smallest valid
one, score it, then score the reference method served over HTTP, so you see what a score is and
how your method compares.

### Step 7. Write a first method

Make a folder for your files and write a method that never claims a finding. Replace its body
with your own logic later. The reference method in `src/sn87_provenonce/miners/witness_ic.py` is
a worked example written from the public contract only.

```bash step id=make-method silent
mkdir -p my-miner
cat > my-miner/my_method.py <<'EOF'
"""A first method: it never claims a finding. Replace the body with your own logic."""


def answer(capsule):
    return {
        "schema_version": capsule["schema_version"],
        "qid": capsule["qid"],
        "capsule_commitment": capsule["evidence_commitment"],
        "method": "my_first_method",
        "state": "INSUFFICIENT_EVIDENCE_ABSTAIN",
        "rationale": "This method abstains on every capsule.",
        "findings": [],
    }
EOF
```

### Step 8. Write a scoring script

This script is your test loop. It builds each public fixture capsule, sends it to your method,
and scores the answer with the public scorer against the published truth. The target is either
`module:function` (called in this process) or the address of a local server.

```bash step id=make-scorer silent
cat > my-miner/score_local.py <<'EOF'
"""Score a method on the three public fixtures against their published truth."""
import sys
import urllib.request

from sn87_provenonce.canonical import canonical_bytes, parse_canonical
from sn87_provenonce.classes import IC_APPROVAL_APPLICABILITY as BINDING
from sn87_provenonce.institutional_v02.fixtures import build_case
from sn87_provenonce.miner_node.core import load_method
from sn87_provenonce.quickstart import FAMILIES, load_public_truth
from sn87_provenonce.scoring import Integrity, score_response, wire

target = sys.argv[1]
truth = load_public_truth()
if target.startswith("http://127.0.0.1"):
    opener = urllib.request.build_opener(urllib.request.ProxyHandler({}))

    def ask(capsule):
        request = urllib.request.Request(target + "/cmt", data=canonical_bytes(capsule),
                                         method="POST")
        with opener.open(request, timeout=30) as reply:
            return parse_canonical(reply.read())
else:
    method = load_method(target)

    def ask(capsule):
        sent = parse_canonical(canonical_bytes(capsule))
        return parse_canonical(canonical_bytes(method(sent)))

integrity = Integrity(True, True, True, True, True, True)  # asserted here; transport supplies it
for family in FAMILIES:
    entry = truth["cases"][family]
    capsule = build_case(family)
    assert capsule["evidence_commitment"] == entry["capsule_commitment"], family
    response = ask(capsule)
    row = wire(score_response(BINDING, capsule, entry["truth"], response, integrity))
    print(f"{family}: answered {response['state']}, truth {entry['truth']['state']}, "
          f"score {row['score']}, valid {row['valid']}")
EOF
```

### Step 9. Score your method

```bash step id=score-mine
uv run --extra transport python my-miner/score_local.py my_method:answer
```

```text expect
re: stale_authority: answered INSUFFICIENT_EVIDENCE_ABSTAIN, truth FINDINGS, score \S+, valid True
re: fresh_review: answered INSUFFICIENT_EVIDENCE_ABSTAIN, truth NO_MATERIAL_DEVIATION, score \S+, valid True
re: incomplete: answered INSUFFICIENT_EVIDENCE_ABSTAIN, truth INSUFFICIENT_EVIDENCE_ABSTAIN, score \S+, valid True
```

The answers are valid, so they are scored, but an abstain earns only the profile's epsilon floor,
a tiny number written in scientific notation, whether or not abstaining was right. A method that
always abstains therefore earns almost nothing. Edit `my-miner/my_method.py`, run this step again
and watch the numbers move; that is the loop.

### Step 10. Serve the reference method over HTTP and score it

`sn87-miner serve --unsigned-loopback` is the development server: canonical capsule bytes in,
canonical response bytes out, no key, no signature, loopback only. The block starts it in the
background on a free port it picks, waits for it, checks that this process is the one running,
scores it, and stops it. In your own shell you can run the first
command in a second terminal instead.

```bash step id=serve-loopback timeout=180
PORT=$(uv run --extra transport python -c \
  'import socket; s = socket.socket(); s.bind(("127.0.0.1", 0)); print(s.getsockname()[1])')
uv run --extra transport sn87-miner serve --unsigned-loopback --role candidate --port "$PORT" \
  > my-miner/loopback.log 2>&1 &
SERVER=$!
for _ in $(seq 1 60); do
  curl --noproxy '*' -fs "http://127.0.0.1:$PORT/health" > /dev/null && break
  sleep 1
done
kill -0 "$SERVER"   # fails if the server just started is not the one that answered
curl --noproxy '*' -s "http://127.0.0.1:$PORT/health"; echo
uv run --extra transport python my-miner/score_local.py "http://127.0.0.1:$PORT"
kill "$SERVER"
wait "$SERVER" || true
```

```text expect
re: \{"class_id": "IC-APPROVAL-APPLICABILITY", "cmt_commitment": "sha256:[0-9a-f]{64}", "cmt_verified": true, .*"role": "candidate", "status": "ok"\}
stale_authority: answered FINDINGS, truth FINDINGS, score 1, valid True
fresh_review: answered NO_MATERIAL_DEVIATION, truth NO_MATERIAL_DEVIATION, score 1, valid True
re: incomplete: answered INSUFFICIENT_EVIDENCE_ABSTAIN, truth INSUFFICIENT_EVIDENCE_ABSTAIN, score \S+, valid True
```

The reference method scores 1 on the two cases that have an answer to find. The server compiled
the task description (the CMT) at start-up and checked its commitment before it listened; the
`cmt_verified` field says so. This server is for development only. Validators do not call it.

The scores above are the same scores the demo showed, for the same fixtures, computed by the same
scorer. They are not a ranking: see "Honest limits".

## Part D. The signed endpoint, the probe and the announcement

The endpoint a validator calls is `sn87-miner serve` without `--unsigned-loopback`:
`POST /v1/assurance`, authenticated with the SDK's `btauth/1` envelope over the exact request
bytes, a replay store that refuses requests when it cannot prove freshness, and a signed response.
It never touches a chain. The design is in
[ADR-0005](../architecture/ADR-0005-signed-http-and-replay-boundary.md).

### Step 11. Generate a throwaway key for this rehearsal

The key is written to a file only you can read (mode 0600) and its secret text is never printed.
It is not a wallet key. Never register it, never fund it, and never put a real key in this folder.

```bash step id=make-key
uv run --extra transport python - <<'EOF'
import os
from bittensor import sp_core

path = "my-miner/throwaway.key"
if os.path.exists(path):  # run again: keep the key you already have
    phrase = open(path).read().strip()
else:
    phrase = sp_core.Keypair.generate_mnemonic()
    fd = os.open(path, os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)
    with os.fdopen(fd, "w") as stream:
        stream.write(phrase + "\n")
address = sp_core.Keypair.create_from_mnemonic(phrase).ss58_address
with open("my-miner/hotkey.ss58", "w") as stream:
    stream.write(address + "\n")
print("throwaway hotkey (this rehearsal only):", address)
EOF
```

```text expect
re: throwaway hotkey \(this rehearsal only\): 5[1-9A-HJ-NP-Za-km-z]{46,47}
```

Your address differs from every other reader's. It is public: it is what a validator would list
for your uid.

### Step 12. Start a replay store

The signed endpoint needs a Valkey-compatible server whose eviction policy is `noeviction` (the
default of Valkey and Redis). A container is the shortest route. This is the only command in the
guide that the runner cannot run for you, because it needs Docker:

```bash display
docker run -d --name sn87-replay -p 127.0.0.1:6379:6379 \
  valkey/valkey:9.1.2@sha256:418652cfb58ef879d4978c33553735d7147016032d5aefaa14c828e611eb9dfd
export SN87_VALKEY_URL=redis://127.0.0.1:6379/0
```

A `valkey-server` or `redis-server` from your package manager, listening on `127.0.0.1:6379`, works
the same way: export the same variable.

The commands below read the store address from the variable `SN87_VALKEY_URL`. When the runner
runs this guide it starts a private store itself, on a socket, and sets the variable; that is why
the steps that use it carry the marker `requires-valkey`. A new store refuses requests
(`REPLAY_STORE_WARMING`) for one freshness window, about 13 seconds, so a restart cannot re-admit
an old request.

Nothing is started. The key is loaded, the method is imported, the store is pinged and its

### Step 14. Sign an announcement

A hotkey says who a miner is, not where it listens. The announcement is one record, signed by your
hotkey, that says where. The format, the verification rules and the discovery rule are in
[miner-announcement.md](../protocol/miner-announcement.md). The first command signs a record for
a public HTTPS origin (the host `example.invalid` stands for yours) and prints what the on-chain
endpoint record would contain. The second verifies the record.

```bash step id=announce
uv run --extra transport sn87-miner announce --hotkey-keyfile my-miner/throwaway.key --netuid 582 \
  --endpoint https://example.invalid:8443 --valid-days 7 --out my-miner/announcement.json \
  --axon-dry-run
uv run --extra transport sn87-miner verify-announcement my-miner/announcement.json --netuid 582 \
  --hotkey "$(cat my-miner/hotkey.ss58)"
```

### Step 15. Serve the signed endpoint, probe it and fetch the announcement

The block starts your method behind the signed endpoint with the announcement attached, waits
until `/ready` answers (the store's start-up window, about 13 seconds), runs `probe`, fetches the
announcement from the well-known path, and stops the server. `probe` sends one fixture capsule
from a throwaway caller key, with its own replay store, and verifies the signed response. The
first probe waits out the caller-side start-up window as well, so the block takes about half a
minute. In your own shell, run the `serve` command in a second terminal.

```bash step id=serve-signed requires-valkey timeout=300
PORT=$(uv run --extra transport python -c \
  'import socket; s = socket.socket(); s.bind(("127.0.0.1", 0)); print(s.getsockname()[1])')
PYTHONPATH=my-miner uv run --extra transport sn87-miner serve --method my_method:answer \
  --hotkey-keyfile my-miner/throwaway.key --valkey-url-env SN87_VALKEY_URL \
  --announcement my-miner/announcement.json --netuid 582 --port "$PORT" \
  > my-miner/serve.log 2>&1 &
SERVER=$!
for _ in $(seq 1 90); do
  curl --noproxy '*' -fs "http://127.0.0.1:$PORT/ready" > /dev/null && break
  sleep 1
done
kill -0 "$SERVER"   # fails if the server just started is not the one that answered
uv run --extra transport sn87-miner probe --endpoint "http://127.0.0.1:$PORT" \
  --miner-hotkey "$(cat my-miner/hotkey.ss58)" --valkey-url-env SN87_VALKEY_URL
curl --noproxy '*' -fs "http://127.0.0.1:$PORT/.well-known/sn87-miner-announcement.json" \
  | cmp - my-miner/announcement.json && echo "announcement served unchanged"
kill "$SERVER"
wait "$SERVER" || true
```

```text expect
probe OK: signed request answered and verified; state=INSUFFICIENT_EVIDENCE_ABSTAIN findings=[]
announcement served unchanged
```

`probe OK` means a request signed by another key reached your endpoint, passed authentication and
replay checks, was answered by your function, and came back signed by your hotkey, with the
signature verified. With `--role candidate` the same probe prints
`state=FINDINGS findings=['STALE_APPROVAL']`. For a real endpoint, `--endpoint` is your HTTPS
origin, and `--miner-hotkey` is your registered hotkey.

### Step 16. The discovery rule, in short

How a validator finds you is a specification, written in full in
[miner-announcement.md](../protocol/miner-announcement.md). In short, for a uid on the metagraph:

1. If the chain's endpoint record for the uid has a non-zero IP and port, fetch
   `/.well-known/sn87-miner-announcement.json` from it. Otherwise use signed announcement files
   from an intake the validator operator has configured.
2. Accept a record only if it is at most 4,096 bytes, canonical, signed by the hotkey the chain
   lists for that uid, for this netuid, not expired, not from the future, and with a sequence
   higher than the last one accepted. Re-sign with a higher sequence whenever anything changes.
3. Send the signed exchange to the `endpoint` in the record, never to the chain address.
4. With no valid record, the uid is not queried that round.

The validator-side reader that applies this rule is not part of this repository, and which route
testnet 582 supports is an open decision listed in that document. Do not assume any validator is
reading your announcement.

## Part E. Registration and test funds on 582

These are actions you take with your own wallet and tools, outside this repository. The guide
does not perform them, does not create a wallet, and sends nothing to a chain.

1. **Wallet.** Create or choose a coldkey and a hotkey with a wallet tool of your own. The hotkey
   is the key you will pass to `--hotkey-keyfile` or `--hotkey-env`. It must be an sr25519 key. The
   throwaway key from Part D must not be used.
2. **Test funds.** Registration costs a burn, paid in test TAO, which has no value. This
   repository does not send funds and does not name a source of them.
3. **The cost.** Read it now from the chain. The next step does a read-only query through
   `scripts/chain_read.py`, which holds no key and has no write path. The cost changes over
   time, so read it again immediately before you register, and compare it with what your
   registration tool shows you before you confirm.
4. **Register** the hotkey on netuid 582 with your wallet tool. That is a chain write, and it is
   yours to sign and send.
5. **Your uid.** Note the uid your registration tool reports. Check that the hotkey address it
   shows is the same one `sn87-miner serve` prints on its `hotkey:` line.
6. **Serve and announce for real.** Put your endpoint behind a TLS reverse proxy, sign an
   announcement for that HTTPS origin with your registered hotkey (Step 14, with your key and
   origin), and serve it with `--announcement`. Use `--hotkey-env` or a 0600 key file; the key is
   read inside the process and never printed. Publishing the on-chain endpoint record is
   optional, is a chain write, and is yours to sign and send.

## Part F. The first score on 582

**Depends on admission to the shadow cohort.**

The check this guide is meant to end with is:

> uid N received a non-zero score in window W on 582.

The shadow cohort is described in [shadow-cohort.md](shadow-cohort.md), with how to apply and the
criteria. This guide does not claim that any uid is on the allowlist, that a window has run, or
that any result is published; look at the published results to see. The check cannot be done until
all of the items below exist for your uid. The route is in
[admission.md](../protocol/admission.md): a uid goes from registered to `shadow` (scored and
published with weight 0) to `weighted`, one approved plan version per step. For the check above,
all of these must exist:

1. **An admission decision.** Your uid on the shadow allowlist, through the application and review
   steps in [shadow-cohort.md](shadow-cohort.md). The tooling in this repository
   (`scripts/admission_plan.py`) builds and checks plan versions; it approves nothing. The weight
   rows on 582 name uids 1 and 2 only, both operated by Provenonce (the uid table in the
   [README](../../README.md)); a shadow uid is not in a weight row.
2. **A valid announced endpoint for your uid.** An endpoint record that passes the checks in
   admission.md and names your hotkey, found through the discovery rule in Step 16. The
   validator-side reader and the shadow tooling that queries your endpoint are operator-only and
   are not in this repository.
3. **A published result for a closed window W.** One per-window record per uid, produced by the
   public scorer under a committed profile, in the format of
   [window-results.md](../protocol/window-results.md). A window is scored on capsules generated
   after you answered, so a score on the public fixtures (Part C) is not one.
4. **Your uid in that record, with a non-zero estimate.** A shadow result has weight 0 by
   construction: it is a score, not a weight. Only a later `weighted` stage, with its own approval
   record, can put your uid in a weight row on 582.

What you will do when it exists: take the uid from Part E, open the published result for the
window, find your uid in it, and read the row the same way you read the rows in Part C. Until the
four items above exist, do not report that a miner has been scored on 582. A report that says "my
uid was scored" before then is a mistake to be investigated, not a result.

## Part G. Troubleshooting by error code

Every `sn87-miner` command that cannot proceed prints `MINER REFUSED: <CODE>` to standard error
and exits with code 2. The signed endpoint answers a failed request with a canonical JSON body
`{"error": "<CODE>"}` and an HTTP status. `probe` prints `MINER REFUSED: PROBE_FAILED: <CODE>`.
The codes below are the ones in the source; a test checks this table against the code, so a code
that is added or removed there fails the build until this table is updated. Codes never contain
key text or record contents.

### Starting `sn87-miner`

| Code | What it means | What to do |
| --- | --- | --- |
| `TRANSPORT_EXTRA_MISSING` | The chain library or web stack is not installed. | Install with `uv sync --locked --extra transport` and run with `uv run --extra transport`. |
| `METHOD_REQUIRED` | No method was chosen. | Give `--role candidate`, `--role baseline`, or `--method module:function`. |
| `METHOD_PATH_INVALID` | `--method` is not of the form `package.module:function`. | Fix the path. |
| `METHOD_NOT_FOUND` | The module or function cannot be imported. | Run from the folder that holds it with `PYTHONPATH=folder`, and check the spelling. |
| `METHOD_NOT_CALLABLE` | The name exists but is not a function. | Point `--method` at a function. |
| `PORT_INVALID` | `--port` is outside 1 to 65535. | Choose a valid port. |
| `NON_LOOPBACK_HOST_REFUSED` | `--host` is not loopback (or, for the unsigned server, not resolvable to loopback). | For the signed endpoint add `--allow-non-loopback` and put TLS in front. The unsigned server never allows it. |
| `UNSUPPORTED_HOST_FORM_USE_127.0.0.1_OR_::1` | The unsigned server was given a host in an unsupported form. | Use `127.0.0.1` or `::1`. |
| `MAX_INFLIGHT_INVALID` | `--max-inflight` is outside 1 to 64. | Choose a value in range. |
| `UNSIGNED_LOOPBACK_TAKES_NO` | A key, store, announcement or `--method` flag was given with `--unsigned-loopback`. | Remove the listed flags; the unsigned server takes `--role` only. |
| `VALKEY_URL_SOURCE_REQUIRED` | Neither or both of `--valkey-url` and `--valkey-url-env` were given. | Give exactly one. |
| `VALKEY_URL_ENV_UNSET` | The named environment variable is empty or unset. | Export it, for example `export SN87_VALKEY_URL=redis://127.0.0.1:6379/0`. |
| `VALKEY_URL_INVALID` | The store address does not parse, or the store cannot be set up with it. | Check the address. It is never echoed, so a password stays out of the output. |
| `VALKEY_URL_SCHEME_INVALID` | The scheme is not `redis`, `rediss` or `unix`. | Use one of those. |
| `NETUID_REQUIRED` | `--announcement` was given without `--netuid`. | Add `--netuid 582`. |
| `ANNOUNCEMENT_FILE_UNREADABLE` | The announcement file cannot be read. | Check the path and the permissions. |
| `PREVIOUS_ANNOUNCEMENT_INVALID` | `--previous` does not name a record for this hotkey and netuid. | Give the record you are replacing, or omit the flag. |
| `SEQUENCE_NOT_INCREASING` | The sequence is not higher than the previous record's. | Omit `--sequence`, or choose a larger one. |
| `SEQUENCE_EXHAUSTED` | The previous sequence is at its maximum. | A record cannot follow it; contact the maintainers through an issue. |
| `OUTPUT_NOT_WRITTEN` | `--out` could not be created. | The file must not exist yet. Choose a new name or folder. |
| `CMT_HASH_VERIFICATION_FAILED` | The task description's commitment did not verify at start-up. | Your checkout is altered or incomplete. Clone again. |
| `CMT_PROFILE_COMMITMENT_MISMATCH` | The task description names a different scoring profile. | Clone again. |
| `CMT_CLASS_MISMATCH` | The task description names a different task class. | Clone again. |

### The hotkey

| Code | What it means | What to do |
| --- | --- | --- |
| `HOTKEY_SOURCE_REQUIRED` | Neither or both of `--hotkey-keyfile` and `--hotkey-env` were given. | Give exactly one. |
| `HOTKEY_ENV_UNSET` | The named environment variable is empty or unset. | Export it. The value is never printed. |
| `HOTKEY_FILE_UNREADABLE` | The key file cannot be opened. | Check the path and who owns the file. |
| `HOTKEY_FILE_NOT_REGULAR` | The path is not an ordinary file. | Point at the key file. |
| `HOTKEY_FILE_PERMISSIONS_TOO_OPEN` | Group or others can read the key file. | Run `chmod 600` on it. |
| `HOTKEY_FORMAT_UNRECOGNIZED` | The text is not a wallet hotkey file, a `0x` seed of 64 hex digits, or a mnemonic of 12, 15, 18, 21 or 24 words. | Supply one of those forms. |
| `HOTKEY_ENCRYPTED` | The key file is encrypted. | Decrypt it into a file only you can read, or give the seed or mnemonic through an environment variable. |
| `HOTKEY_NOT_SR25519` | The key is not sr25519. | Use an sr25519 hotkey. |

### Signing and verifying the announcement

All of these begin with `ANNOUNCEMENT_`. The rules are in
[miner-announcement.md](../protocol/miner-announcement.md). The `AXON` and `FETCH` codes
are reported by a validator that reads your record; you see them when you test the fetch rule
yourself or when a validator operator tells you.

| Code | What it means | What to do |
| --- | --- | --- |
| `ANNOUNCEMENT_ENDPOINT_INVALID` | The endpoint is not a plain origin: it has a path, query, credentials, a zero port, an odd host form or non-printable text. | Use a plain `https` origin: scheme, name, optional port, nothing else. |
| `ANNOUNCEMENT_ENDPOINT_NOT_GLOBAL` | The host is `localhost` or an address that is private, loopback, link-local or reserved. | Announce your public origin. For local tests only, add `--allow-loopback-endpoint`. |
| `ANNOUNCEMENT_ENDPOINT_NOT_HTTPS` | The scheme is not `https`. | Put TLS in front and announce the `https` origin. |
| `ANNOUNCEMENT_FIELD_INVALID` | A field has the wrong type or range, for example a negative sequence or a netuid outside 0 to 65535. | Fix the value. |
| `ANNOUNCEMENT_VALIDITY_WINDOW_INVALID` | The record expires before it is issued, or lives longer than 30 days. | Use `--valid-days` between a small positive number and 30. |
| `ANNOUNCEMENT_SIGNER_MISMATCH` | The signature names a signer other than the hotkey in the record. | Sign with the hotkey you announce. |
| `ANNOUNCEMENT_SIGNATURE_INVALID` | The signature does not verify. | The file changed after signing. Sign it again. |
| `ANNOUNCEMENT_TOO_LARGE` | The record is over 4,096 bytes. | Do not edit it by hand; sign it again. |
| `ANNOUNCEMENT_NOT_CANONICAL` | The bytes are not canonical JSON. | Do not reformat the file; sign it again. |
| `ANNOUNCEMENT_SCHEMA_INVALID` | The fields are not exactly the ones the format names. | Sign it again with this version of `sn87-miner`. |
| `ANNOUNCEMENT_WRONG_NETUID` | The record names a different netuid than the one checked. | Pass `--netuid 582` when signing and verifying. |
| `ANNOUNCEMENT_WRONG_HOTKEY` | The record's hotkey is not the one expected. | Check you are serving with the hotkey you announced. |
| `ANNOUNCEMENT_ISSUED_IN_FUTURE` | The record was issued more than 5 minutes ahead of the checking clock. | Check your clock. |
| `ANNOUNCEMENT_EXPIRED` | The record has expired. | Sign a new one with a higher sequence (`--previous OLD.json`). |
| `ANNOUNCEMENT_SEQUENCE_ROLLBACK` | The sequence is lower than one already accepted for this hotkey. | Sign a new record with a higher sequence. |
| `ANNOUNCEMENT_SEQUENCE_CONFLICT` | The same sequence was used for different bytes. | Any change needs a new, higher sequence. |
| `ANNOUNCEMENT_AXON_INVALID` | The on-chain endpoint record holds an address or port that cannot be used (validator side). | Publish a valid IP address and port, or rely on the signed announcement. |
| `ANNOUNCEMENT_AXON_NOT_GLOBAL` | The on-chain endpoint record names a private, loopback or reserved address (validator side). | Publish a globally routable address. |
| `ANNOUNCEMENT_FETCH_URL_INVALID` | The validator could not build a fetch address from the chain record. | Check the on-chain record's IP and port. |
| `ANNOUNCEMENT_FETCH_ADDRESS_NOT_GLOBAL` | The address to fetch from is not globally routable, so the validator will not connect. | Serve from a public address. |
| `ANNOUNCEMENT_FETCH_RESOLVE_FAILED` | The host name did not resolve. | Fix your DNS. |
| `ANNOUNCEMENT_FETCH_CONNECT_FAILED` | The validator could not connect. | Check the port, firewall and that the server is running. |
| `ANNOUNCEMENT_FETCH_TIMEOUT` | The fetch took too long. | Serve the record quickly; it is a small static file. |
| `ANNOUNCEMENT_FETCH_REDIRECT_REFUSED` | The path redirected. Redirects are never followed. | Serve the record directly at the well-known path. |
| `ANNOUNCEMENT_FETCH_STATUS_REFUSED` | The server answered with a status other than 200. | Serve the file at `/.well-known/sn87-miner-announcement.json` with status 200. |
| `ANNOUNCEMENT_FETCH_TOO_LARGE` | The response is over 4,096 bytes. | Serve only the signed record. |

### What the signed endpoint answers

These are the `error` values a caller receives, with the HTTP status in the column. A validator
sees the same ones.

| Code | Status | What it means | What to do |
| --- | --- | --- | --- |
| `REPLAY_STORE_UNAVAILABLE` | 503 | The store does not answer, so freshness cannot be proved and requests are refused. | Start the store, check `SN87_VALKEY_URL`, and see `GET /ready`. |
| `REPLAY_STORE_WARMING` | 503 | The store is new or restarted and refuses requests for about 13 seconds. | Wait for `/ready` to return 200. |
| `REPLAY_STORE_EVICTION_POLICY_UNSAFE` | 503 | The store's `maxmemory-policy` is not `noeviction`. | Set `maxmemory-policy noeviction`. |
| `REPLAY_STORE_EVICTION_POLICY_UNVERIFIABLE` | 503 | The policy cannot be read, for example the `CONFIG` command is disabled. | Allow `CONFIG GET` for this client. |
| `RATE_LIMITED` | 429 | The caller sent too many requests in a minute. | Slow down. |
| `CAPACITY_LIMIT` | 429 | All request slots are busy. | Retry; raise `--max-inflight` if your method is fast. |
| `AUTHENTICATION_FAILED` | 401 | The `btauth/1` signature, age or receiver check failed. | Check the caller's clock and the hotkey it addresses. |
| `AUTHENTICATION_UNAVAILABLE` | 401 | Authentication hit an unexpected failure. | Retry; report it if it persists. |
| `REPLAYED_REQUEST` | 401 | This signed request was already seen. | Sign a fresh request each time. |
| `DUPLICATE_HEADER` | 400 | A header appears twice. | Send each header once. |
| `INVALID_CONTENT_LENGTH` | 400 | `Content-Length` is not a number. | Send a valid length. |
| `TRUNCATED_BODY` | 400 | The body is shorter than announced, or the caller left. | Send the whole body. |
| `UNSUPPORTED_PATH` | 404 | Wrong path, or a query string was present. | Use `POST /v1/assurance` with no query. |
| `UNSUPPORTED_MEDIA_TYPE` | 415 | The content type is not `application/json`. | Send exactly that type. |
| `UNSUPPORTED_CONTENT_ENCODING` | 415 | The body is compressed. | Send it uncompressed. |
| `BODY_TOO_LARGE` | 413 | The body is over the wire limit. | Keep the request within the limit in the transport document. |
| `INVALID_ENVELOPE` | 422 | The request does not have exactly the envelope fields. | Build the request with `pilot.client.prepare_request`. |
| `INVALID_PAYLOAD` | 422 | The body does not parse, or a field is invalid. | Check the canonical encoding. |
| `CHALLENGE_BINDING_FAILED` | 422 | The envelope's challenge id differs from the capsule's `qid`. | Make them equal. |
| `DEADLINE_REJECTED` | 408 | The deadline is already past, or too far ahead. | Set a deadline a few seconds from now; check the caller's clock. |
| `DEADLINE_EXCEEDED` | 504 | Your method answered after the deadline. | Make the method faster; a late answer counts as a failure. |
| `HANDLER_BINDING_FAILED` | 500 | Your method returned something that is not a differential for this `qid`. | Return one differential dict whose `qid` equals the capsule's. |
| `INTERNAL_FAILURE` | 500 | Your method raised an error. | Run it with `score_local.py` to see the exception. |

| Code | What it means | What to do |
| --- | --- | --- |
| `PROBE_FAILED` | The probe did not complete. The text after the colon is a code below, or the name of the error, such as `ConnectError` when nothing answers at `--endpoint`. | Check the endpoint is running and the address is right. |
| `REMOTE_REJECTED` | The endpoint answered with a status other than 200. | Look in the server log and the table above for the code it sent. |
| `RESPONSE_TOO_LARGE` | The response is over the wire limit. | Return a smaller differential. |

## Honest limits

Read these before you judge what you saw. [LIMITATIONS.md](../../LIMITATIONS.md) has the full
list.

- **No outside miner is weighted on 582.** The weight rows name uids 1 and 2, which Provenonce
  operates. A shadow cohort is described in [shadow-cohort.md](shadow-cohort.md) (shadow results
  are scored and published with weight 0). This guide does not claim any uid is enrolled, and no
  outside uid is known to be scored by this repository's tooling; nothing in this guide can show
  you a score on the network.
- **Parts C and D are rehearsals.** The scorer, the wire and the signatures are the real code,
  but the capsules are the three public fictional fixtures, the key is a throwaway, the replay
  store is yours, and the integrity checks are asserted locally in the scoring script. A score
  from the scripts here is not a score on 582.
- **The announcement route is undecided.** The record format and its checks are implemented and
  tested. The validator-side reader and the supported route on 582 are not in this repository.
- **Fixtures are not a ranking.** The truth of the public fixtures is published; the truth of
  hidden instances is private. Both reference methods are Provenonce code, and on the public
  fixtures they show no measured headroom over the matched baseline. Do not expect scores to
  rank competing methods yet.
- **Alpha, testnet only.** Plain weight mode, no commit-reveal. Test TAO has no value. Nothing
  here says anything about the main network or about adoption.
- **No capacity figures.** No hardware, latency or throughput numbers are published.
